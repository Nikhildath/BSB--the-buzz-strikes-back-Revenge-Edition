The Idea That Shouldn't Exist

It started with a question nobody asked: what if mosquitoes had to listen to their own annoying buzzing? Not as revenge. Not as justice. Just as science.

The concept was simple. Two ESP32 boards. One controls the trap hardware (LED, speaker, zapper, sensors). The other handles the UI (OLED display, touch buttons, web dashboard). They talk to each other via ESP-NOW at 2.4GHz with zero internet dependency.

We named it BSB — Buzz Strikes Back. Because every good project needs an aggressive name.

Breadboard Chaos and Pin Wars

Hardware day. The desk looked like a bomb went off in an electronics store. Two ESP32 DevKit boards, OLED display, IR sensor, HC-SR04 ultrasonic, blue LEDs, MOSFETs, a MAX98357A amplifier, speaker, touch sensors, and a high-voltage boost module.

The workspace. Somewhere in this chaos is a mosquito trap.

The wiring was... ambitious. ESP32 #1 (Trap Controller) needed:

ESP32 #1 — Trap Controller ================================ GPIO 25 ──── Blue LED (via IRLZ44N MOSFET) GPIO 26 ──── IR Break-Beam Sensor GPIO 27 ──── HC-SR04 Trigger GPIO 14 ──── HC-SR04 Echo (voltage divider!) GPIO 5 ──── MAX98357A BCLK GPIO 18 ──── MAX98357A LRC GPIO 19 ──── MAX98357A DIN GPIO 22 ──── MAX98357A SD/EN (amp enable) GPIO 32 ──── Zapper MOSFET Gate GPIO 33 ──── Status LED

GPIO 14 kept causing problems. It's a strapping pin on ESP32 and also shares functionality with the SDIO peripheral. We almost fried an HC-SR04 before realizing the echo pin needs a voltage divider (3.3V safe) since the sensor runs on 5V.

The Firmware That Almost Worked

Firmware day. The code was split across two ESP32 boards with a shared protocol header. 16-byte packed structs with XOR checksum validation. Very serious engineering for a mosquito torture device.

The ESP-NOW callback signatures became our first major battle. Arduino IDE uses ESP32 core 3.3.11 which expects esp_now_recv_info* in the receive callback. PlatformIO uses core 4.4.7 which expects const uint8_t*. Same chip, different API. We had to maintain both.

Then PlatformIO's .ino converter decided to have a meltdown. Large HTML strings in R"rawliteral(...)rawliteral" format broke the parser completely. The fix? Move all HTML into a separate index_html.h header file. 

// mosquito_protocol.h — the language of trap-to-gateway communication
struct TrapMessage {
  uint8_t msgType;
  uint8_t deviceId;
  uint32_t timestamp;
  uint8_t ledState;
  uint8_t ledBrightness;
  uint8_t buzzState;
  uint8_t irState;
  uint8_t distanceCM;
  uint8_t operatingMode;
  uint16_t detectionCount;
  uint8_t errorFlags;
  uint8_t checksum;
};

The enum : uint8_t syntax also broke PlatformIO. So we moved to plain #define. PlatformIO's .ino converter has opinions, and those opinions are loud.

By midnight, PlatformIO was building cleanly. We had 36 files committed in one massive push.

🎵 the speaker saga

Speaker Debugging: A Horror Story

We swapped from PAM8403 (PWM amplifier) to MAX98357A (I2S amplifier). Clean digital audio, no PWM noise. Seemed like an upgrade. It was not.

First attempt: speaker produced nothing. Serial showed I2S driver installed successfully, pins configured, no errors. But silence. Complete, absolute silence.

The bugs were everywhere:

  • Phase reset bug — sine wave was recalculated from t=0 every buffer. No continuous waveform.
  • Volume overflow — speakerVolume was uint8_t (0-255) but MOSQUITO_VOLUME was 8000. Integer overflow = garbage audio.
  • Missing amp enable — MAX98357A SD/EN pin needs HIGH to wake up. We weren't driving it at all.
  • Wrong comm format — I2S_COMM_FORMAT_STAND_I2S should have been I2S_COMM_FORMAT_STAND_MSB for MAX98357A.
  • Buffer too small — 256 samples caused frequent underflow. Bumped to 512.

The fix that finally worked: a persistent speakerPhase accumulator that never resets, non-blocking i2s_write() with timeout=0, and GPIO 22 driving the amp enable pin HIGH on boot. 

// The fix — continuous sine wave with persistent phase
float amplitude = ((float)state.speakerVolume / 255.0f) * MOSQUITO_VOLUME;
for (int i = 0; i < I2S_BUFFER_SIZE; i += 2) {
  float sample = sinf(state.speakerPhase) * amplitude;
  samples[i] = (int16_t)constrain(sample, -32767.0f, 32767.0f);
  samples[i + 1] = samples[i]; // stereo
  state.speakerPhase += 2.0f * PI * state.currentFreq / (float)I2S_SAMPLE_RATE;
  if (state.speakerPhase >= 2.0f * PI) state.speakerPhase -= 2.0f * PI;
}
size_t bytes_written = 0;
esp_err_t err = i2s_write(I2S_PORT, samples, sizeof(samples), &bytes_written, 0);

Then: sound. A beautiful, annoying 450Hz mosquito buzz. The kind that makes you want to leave the room. Perfect.

We also added the ESP32-Eyes emotic display library (22 files copied into the project). The OLED now shows animated eyes that change based on trap state. Happy when idle, angry when buzzing, scared when lifted. No text. Just vibes.

Ultrasonic Woes and README Therapy

The HC-SR04 ultrasonic sensor refused to cooperate. It was reading distances fine, but the lift detection — the feature that shows a scared face on the OLED when someone picks up the trap — wasn't triggering.

The read interval was 5 seconds. The lift check ran every 1 second. So 4 out of 5 lift checks used stale data. Bumped the read rate to 1Hz and added serial diagnostic output so we could actually see what the sensor was reading.

Also rewrote the entire README from a boring technical doc to the TinkerHub Useless Projects template. Because if your project doesn't have a section called "The Problem (that doesn't exist)", is it even a useless project?
